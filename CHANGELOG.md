# Changelog

All notable changes to TRANSFORM are recorded in this file.

The format follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/). Each change adds a line under **Unreleased**. When a version is released, its section is also summarized in `TRANSFORM.UsersGuide.ReleaseNotes`, the release-notes package inside the library, as the Modelica Standard Library does.

## [Unreleased]

### Added

- `TRANSFORM.Math.ComplexMath.ccubicRoots` has two new outputs, `re[3]` and `im[3]`: the same roots as `Real` arrays. OpenModelica 1.27.1 cannot set an array of `Complex` records in a model from a function call, so a model that must run there writes `(, nRoots, re, im) = ccubicRoots(a, b, c, d)`. Existing calls are unchanged. The examples `TRANSFORM.Math.Examples.check_cubicRoots` and `TRANSFORM.Math.Examples.ComplexMath.check_ccubicRoots` use the new outputs and now run in OpenModelica; their Dymola results are unchanged. Upgrade note: a function of your own that replaces `ccubicRoots` through a `replaceable` declaration constrained by it must now also declare the outputs `re[3]` and `im[3]`; one that extends `ccubicRoots` must not declare its own `re` or `im`.

### Changed

- `TRANSFORM/package.mo`: `main` carries `version="1.2.0-dev"` and adds `noneFromVersion="1.1.0"` to the conversion annotation, so models written for 1.1.0 load without conversion. The release date `versionDate` is removed until the next release.
- `TRANSFORM/package.mo` declares `SDF(version="0.4.5")` in its `uses` annotation. The critical heat flux and film boiling look-up tables (`Groeneveld2006LUT`, `Alphas_TwoPhase_3Region_CHFtransition`, the example `Groeneveld2001LUT_FilmBoilingCoefficient` and the examples of the first two) read their data with `SDF.NDTable`, but the library did not say so (#98). SDF is public under the BSD 2-Clause license. What to do: in Dymola 2026x, nothing; it ships SDF 0.4.6, which loads 0.4.5 models without conversion (older Dymola versions are unchecked). Other users install SDF 0.4.5 from [SDF-Modelica](https://github.com/ScientificDataFormat/SDF-Modelica/releases) or, in OpenModelica, with `installPackage(SDF, "0.4.5")`. Only the models that use these tables need SDF: OpenModelica 1.27.1 loads TRANSFORM without it and prints the install command. With SDF installed, these models also run in OpenModelica and match the Dymola results. `README.md` now lists ExternalMedia and SDF as optional libraries. Results are unchanged.

### Fixed

- `TRANSFORM.Nuclear.ReactorKinetics.Functions.Initial_powerBased_powerHistory`, which gives the start values of the precursor powers `Cs` and decay-heat energies `Es` from a power history (`use_history=true` in `PointKinetics_L1_powerBased`, `PointKinetics_L1_powerBased_sparseMatrix` and the `CoreSubchannels` regions): three fixes. (1) The precursor update had a term `- t[i]` (a time) inside a bracket without units. Without it, the update is the exact solution of the precursor equation over each history interval on which the power is linear (intervals of 1 s or more), as the decay-heat update already was. Precursor start values change wherever the history's power has a slope after its first point. They were too low after rising power and too high after falling power, most in the slowest groups: on a 300-s history of two 100-s ramps the slowest group was 20 % low after rising power, and 21 times too high after falling power. `Es` and the decay power are unchanged. (2) Without decay heat in the history (`includeDH=false`), the start values `Cs_0` and `Es_0` were ignored: the outputs were read before being set, so an empty or one-point history returned whatever the tool left there (0 in Dymola, about 6.5e-310 in OpenModelica). They are now used. (3) Also with `includeDH=false`, a nonzero `Es_0` scaled the history's power down as if it held decay heat; it no longer does. No model in the library passes `Cs_0` or `Es_0`, and the only one with `use_history=true` is the example `Examples.Functions.Initial_powerBased_powerHistory`, whose results move within single-precision storage noise (its last interval is 1e16 s long). Dymola results are otherwise identical (all 335 tests, whole result files compared). Upgrade note: a model with `use_history=true` and a history whose power changes after its first point starts with different precursor powers; the old values were wrong, so there is no option to keep them. Test: `TRANSFORMTest.Nuclear.ReactorKinetics.Functions.PowerHistory_vs_ODE` (in TRANSFORM-UnitTests) checks the function against integrating the same equations.
- `TRANSFORM.HeatAndMassTransfer.ClosureRelations.Geometry.Models` (all 16 conduction geometries: `Cylinder_*`, `Plane_*`, `Sphere_*`): volumes, areas, lengths and positions are now computed in an `equation` section instead of an `algorithm` section. A tool cannot differentiate an algorithm section, so the conduction models (`Conduction_1D/2D/3D` and the walls built on them) could not keep their wall temperatures `materials.T` as states: they fell back to the stored energy `Us`, which has no start value, so `Ts_start` was ignored and the wall started where its stored energy is zero, the material's reference temperature (298.15 K for most solids). In OpenModelica 1.27.1 and 1.27.2 this happened in every such wall and spread to the fluid volumes coupled to it, which lost their pressure and enthalpy states and started with no mass (`SteamWater_HCSG` stopped at p = 0). In Dymola it happened in some models: `Winding_12D_variableArea` and `Winding_123D_variableArea` started at 298.15 K instead of 320 K and end about 25 K too cold; `PbLiTest2` started its permeator wall at 298.15 K instead of 743.15 K (a 1.4e11 W heat burst at t = 0; its efficiency `eta` differs by up to 0.074 between 16 and 45 s, the end value is unchanged); `nParallel_withWall_FlowBoundary` and `_StateBoundary` used `Us` and the trace moles as wall states (their start-up tritium concentrations move by up to 0.2 %). Now the walls keep `materials.T` as states and use `Ts_start`. Dymola results also change slightly in other models with conduction walls, because Dymola sorts the equations differently (`CIET_nureth`, `NSSS_Test`, `IRIS_Default_Test`, `IRIS_Default_Teststandalone`, `withWall`, `withWallx2`, `withWallTrace`, `Example_1_5_1_ThermalProtectionSystem`, `part_c_ThermalElongation`: same start values, normalised differences 1e-4 to 1.6e-3, IRIS 1.4e-2 within its known run-to-run spread); their Dymola baselines are re-accepted. The geometry values themselves are unchanged. In the same change, `GenericDistributed_HX` and `GenericDistributed_HX_withMass` bind the tube wall's cell lengths with `fill(geometry.dlengths_tube, geometry.nR)`, and `StraightPipe`, `StandardPipe`, `StraightDuct`, `StraightAnnulus` and `StraightPipeHX` bind their surface areas with `fill(surfaceArea/nV, nV)`, instead of `transpose({fill(...) for i in ...})`: same values, and Dymola results are bit-identical, but OpenModelica treated the comprehension as time-varying, gave the tube wall a dynamic state set whose start-up failed (`OilWater_PTHX`, `SteamWater_HCSG`) and stopped with an internal error in `WaterWater_STHX_withInsulation`. In OpenModelica, `withWall`, `withWallx2`, `Example_8_6_UninsulatedDuctwithMass`, `SteamWater_HCSG`, `WaterWater_STHX` and `WaterWater_STHX_withInsulation` now run and match Dymola; `Winding_123D` (x3), `withWallTrace`, `WaterWater_STHX_wallR` and `_withMass` still time out there, with the same states as Dymola. Upgrade note: a model with a conduction wall whose `Ts_start` differs from the material's reference temperature may give different results, because the wall now uses `Ts_start` where it did not before. To get the old start back, set `Ts_start` to the material's reference temperature (298.15 K for most solids, 298 K for `UO2`). Tests: `Winding_12D_variableArea`, `PbLiTest2` and `withWall` now also track a wall temperature (TRANSFORM-UnitTests `test_spec.json`).
- `TRANSFORM.Media.Solids.Copper.OFHC_RRR200`: conductivity is now a cubic spline through its table (50–500 K), held at the end values outside it. The inherited degree-2 polynomial fit could not follow the steep rise below 100 K and was off by up to 318 W/(m·K) inside the table (296 instead of 399 at 300 K, 617 instead of 471 at 100 K). Its `electricalResistivity` is changed the same way: its degree-2 fit was 41 % low at 50 K and negative below 45 K. Results of models with OFHC copper change: `TRANSFORM.HeatAndMassTransfer.Examples.ExamplesFrom_NellisAndKlein.Example_1_9_2_CryogenicCurrentLeads` (cold-end heat load 6.44 → 6.74 W, +4.7 %; warm-end heat flow +8.8 %; lead temperatures by up to 18 K) and `TRANSFORM.Examples.CIET_Facility.Examples.CIET_nureth`, whose copper-walled pipe `S11` now conducts up to 27 % differently along its wall (its tracked temperature `RTD40` moves by up to 0.015 %); `CIET_initial` (not a test) also uses it. `PartialSimpleAlloy_TableBased.thermalConductivity` is now `replaceable`, so a material can redeclare it. `TRANSFORM.Media.Solids.Cr225Mo1`: above its table (which ends at 816 °C) conductivity is held at the fit's value there, 25.9 W/(m·K) (the table's last point is 26.48), and below 0 K at its 0 K value; the fit's extrapolation fell to zero at 1627 K and to −9.6 at `T_max` (1500 °C). No TRANSFORM model uses Cr225Mo1. Upgrade note: models with these materials get different conductivity where the old fit was wrong (copper inside 50–500 K and outside it; Cr225Mo1 above 816 °C); to keep the old values, use a package that extends the material and redeclares `thermalConductivity` in full (`redeclare function thermalConductivity` with its `state` input and `lambda` output; `function extends` would add a second algorithm) computing `TRANSFORM.Media.Interfaces.Solids.Polynomials_Temp.evaluate(poly_lambda, state.T)`. Test: `TRANSFORMTest.Media.Solids.AlloyConductivity_TableFits` (copper conductivity and resistivity, Cr225Mo1); `CryogenicCurrentLeads` now also tracks its warm-end heat flow and two lead temperatures. `TRANSFORM.Media.Solids.CustomSolids.Lambda_fT_d_7763_cp_fT`: a comment now says its conductivity line reaches zero at 1638 K and that its source and range are unknown.
- `TRANSFORM.Media.Solids`: every polynomial, table or spline conductivity fit that reaches zero or a pole below 0 K is now evaluated at `max(state.T, 0)`: `SS316`, `SS304`, `SS316_TRACE`, `SS304_TRACE`, `ZrNb_E125`, `FiberGlassGeneric`, `HT9`, `Alumina`, `Helium`, `Graphite.Graphite_1`/`_2`/`_3`, and the table- and spline-based interfaces (`PartialSimpleAlloy_TableBased`: `Inconel690`, `Inconel625`; `PartialSimpleAlloy_SplineBased`: `Molybdenum`, `Tungsten`; `Cr225Mo1` and `Copper.OFHC_RRR200` now have their own conductivity functions, which are held at 0 K and at their table's ends: see their line). The conduction models average the conductivity of two points, so where a fit reaches zero a steady state with no heat flow has a second, false solution (SS316 and SS304 reach zero at −873 K: a wall at −2043 K next to 297 K water). OpenModelica 1.27.1 converged to it while searching for the start of `TRANSFORM.Fluid.Pipes.Examples.GenericPipe_Tests.nParallel_withWall_StateBoundary` and `nParallel_withWall_FlowBoundary`, from the default start guesses, from guesses at the real solution, with and without homotopy, and with its kinsol, hybrid and newton solvers; both now start. No value at a real temperature (0 K and up) changes. In Dymola most results are bit-identical; `CIET_nureth` evaluates fits below 0 K inside its solver iterations, so it moves within its test tolerance (temperatures and pressures by less than 1e-5 %); the two IRIS tests are re-baselined, because the change makes Dymola choose different states in one dynamic state set (pressurizer pressure by up to 0.3 kPa on Linux and 2 kPa on Windows out of 15.4 MPa, core power by up to 0.05 %). Not guarded: `UN` and `UO2` (power laws, undefined below 0 K); fits that reach zero above 0 K (`HT9` at 1961 K and `Rhenium` at 8441 K, above their range; `CustomSolids.Lambda_fT_d_7763_cp_fT` at 1638 K, inside it). Test: `TRANSFORMTest.Media.Solids.AlloyConductivity_FloorAt0K`. The two withWall tests now also track an unheated wall surface, the outlet enthalpy and the outlet tritium (TRANSFORM-UnitTests `test_spec.json`).
- `TRANSFORM.Fluid.Pipes.Examples.GenericPipe_Tests.nParallel_StateBoundary`: both pipes now set `m_flow_a_start=1`, the flow of their mass-flow sources. This also puts the default `p_b_start` 1 kPa below `p_a_start`, so the start guesses for the pipes' steady-state start have a pressure drop, and so a flow. With the default 0, every pressure guess was 101325 Pa, which gives no flow: OpenModelica 1.27.1 then found the start problem's Jacobian singular, drove the pipe enthalpies below the range of the IF97 water tables and could not start, with or without homotopy. The pressure drop is what matters: a flow guess with `p_b_start = p_a_start` still fails. OpenModelica now starts and matches Dymola within 5e-8 of each tracked value. Dymola results are unchanged: every stored signal of magnitude 1e-3 or more that is not a derivative is identical, except one velocity, which moves by one step of single-precision storage (9e-8 of its value). The start converges to a slightly different point, so signals near zero move on solver noise, derivatives change (most at t = 0; after it by at most 0.25 % of their value), and so do the solver's iteration counts. MSL examples set a start flow and start pressures the same way (`Modelica.Fluid.Examples.BranchingDynamicPipes`). The test now also tracks the outlet enthalpy and tritium concentration and the inlet pressure of both pipes (TRANSFORM-UnitTests `test_spec.json`); before, it tracked only fixed boundary values.
- `TRANSFORM.Fluid.Pipes.Examples.GenericPipe_Tests.nParallel_FlowBoundary`: both pipes now set `m_flow_a_start=1`, the flow of their mass-flow sources, as `nParallel_StateBoundary` does (entry above); this also puts the default `p_b_start` 1 kPa below `p_a_start`. With the default 0, OpenModelica's start with global homotopy failed (a start without homotopy worked); with these start guesses it starts with no simulation flag. Dymola results are unchanged: every stored signal of magnitude 1e-3 or more that is not a derivative is identical, except one velocity, which moves by one step of single-precision storage; signals near zero, derivatives (most at t = 0) and the solver's start iterations change. The test now also tracks the outlet enthalpy and tritium concentration and the inlet pressure of both pipes (TRANSFORM-UnitTests `test_spec.json`); before, it tracked only the wall-port temperature and tritium concentration. The outlet values equal what conservation gives (inlet enthalpy plus 1000 W over 1 kg/s; tritium 0.2), in both the single and the 10-parallel pipe.
- `TRANSFORM.Examples.MoltenSaltReactor.Components.DRACS`: every start is now explicit. The pipe pressures still start from steady state (`massDynamics=SteadyStateInitial`, unchanged); every other state starts from its start value: `energyDynamics=FixedInitial` on the four NaK pipes and the four thimble walls, `massDynamics=FixedInitial` on `expansionTank_DRACS` and `waterTank` (`h_start`, `level_start`), and `initType=InitialState` on `PID_waterTank`. With the defaults (`DynamicFreeInitial`, `NoInit`) the start was under-specified and each tool completed it its own way: Dymola started at these same values, OpenModelica fixed pipe pressures at their start values (1.01e5 Pa against about 2.52e5 Pa) and could not start `DRACS_Test`. The change leaves Dymola's results unchanged: `DRACS_Test` and `MSDR_noBOP` pass their Dymola baselines. `DRACS_Test` now runs at tolerance 1e-6 instead of 1e-4 (TRANSFORM-UnitTests `test_spec.json`), because OpenModelica's DASSL stops at t = 11.35 s at 1e-4; its Dymola baselines are re-accepted for that (largest change NRMSE 1.6e-3, on the water-tank inflow). OpenModelica then matches Dymola within 0.12 % of range (the water-tank inflow within 1 %). The test also tracks the riser top and downcomer outlet temperatures and the riser pressure.
- `TRANSFORM.Fluid.Volumes.Examples.Pressurizer_withWall_Test`: the pressurizer now starts with `massDynamics=FixedInitial` and `energyDynamics=FixedInitial`, at `p_start` and `Vfrac_liquid_start`. Its steady-state start (`system.energyDynamics=SteadyStateInitial`) has more than one solution: OpenModelica could not start the example, and Dymola started at `Vfrac_liquid` = 0.356 instead of `Vfrac_liquid_start` = 1/3. Dymola's results change: the level starts at 1.669 m instead of 1.728 m and ends at 3.09 m instead of 3.32 m at t = 1000 s, and the start now has a start-up surge (2500 kg/s out of the pressurizer at t = 0); the Dymola baselines are re-accepted. OpenModelica matches Dymola at the test's settings: the level within 0.06 % of its range, pressure and liquid enthalpy within 2 % and 0.9 %, largest during the start-up surge. The filling of the pressurizer after the start is sensitive to solver details: in OpenModelica, a 0.01 s output step gives no filling at all (level 1.64 m at t = 1000 s). Same start as `Pressurizer_Test` and `Modelica.Fluid.Examples.DrumBoiler.DrumBoiler`. The test also tracks `pressurizer.drum2Phase.p` and `pressurizer.drum2Phase.h_liquid` (TRANSFORM-UnitTests `test_spec.json`). The `Pressurizer_withWall` model is unchanged.
- `TRANSFORM.Fluid.Volumes.Examples.Pressurizer_Test`: the pressurizer now starts with `energyDynamics=FixedInitial` and `massDynamics=FixedInitial`, so it starts at `p_start` and `Vfrac_liquid_start`. Before, it started from steady state (inherited from `system.energyDynamics`). With no flow and no wall heat transfer, every saturated state is steady, so `der(p) = 0` and `der(Vfrac_liquid) = 0` fixed neither pressure nor level. Dymola started near the start values; OpenModelica 1.27.1 needed `-noHomotopyOnFirstTry` to start at all and then started at 1.987 bar instead of 1.013 bar (level 1.7432 m instead of 1.7333 m). Now OpenModelica starts without that flag and matches Dymola's Linux baseline (pressure within 0.2 Pa, level within 4e-5 m). Dymola's result is unchanged within its test tolerance; it now has a short start-up transient (events 3 to 7). `Modelica.Fluid.Examples.DrumBoiler.DrumBoiler` starts its drum the same way. The test now also tracks `drum2Phase.p` and `drum2Phase.Q_vl` (TRANSFORM-UnitTests `test_spec.json`). The `Pressurizer` model itself is unchanged; for `Pressurizer_withWall_Test` see the entry above.
- `TRANSFORM.Nuclear.ReactorKinetics.Functions.Initial_powerBased_powerHistory`: the time and power columns of `history` are now read element by element (`{history[i, 1] for i in 1:nT}`) instead of as slices (`history[:, 1]`). OpenModelica 1.27.1 passed the empty default history `fill(0, 0, 2)` (of `PointKinetics_L1_powerBased`, `PointKinetics_L1_powerBased_sparseMatrix` and the `CoreSubchannels` regions) as a one-dimensional `{}`, and the slice then stopped the simulation at start-up with "index spec dimensions and array dimensions do not agree 2 != 1", even with `use_history=false`. `PointKinetics_Test` and `PointKinetics_vs_ApproximateOneGroup` now run in OpenModelica and match Dymola (within 1e-4 of the largest value). `IRIS_Default_Test` and `IRIS_Default_Teststandalone` now get past this point but still fail later in OpenModelica. Values are the same; Dymola results are unchanged (all 335 tests).
- `TRANSFORM.Fluid.ClosureRelations.HeatTransfer.Models.DistributedPipe_1D_MultiTransferSurface.PartialHeatTransfer_setT`: the wall states `states_wall` are now set with one `setState_pTX` call per element instead of one vectorized call over all of them. OpenModelica 1.27.1 got the vectorized call wrong: it miscounted its equations when the medium has more than one substance and the pipe more than one volume, generated C that did not compile, or failed at start-up. `IncompressibleFluidNetwork`, `RoomCO2WithControls` and `OilWater_PTHX` now run in OpenModelica and match Dymola; `BranchingDynamicPipes` and `BranchingDynamicPipes_MultiSurface` now build there but still fail at start-up (the next entry fixes their start-up). Dymola results are unchanged (all 335 tests).
- `TRANSFORM.Fluid.Examples.MSLFluid.BranchingDynamicPipes` and `BranchingDynamicPipes_MultiSurface`: the two examples now carry the annotation `__OpenModelica_simulationFlags(noHomotopyOnFirstTry="()")`. OpenModelica 1.27.1 starts with global homotopy whenever a model contains `homotopy()` (here through the pipe components), and on these examples that start failed; a start without homotopy works. Both now run in OpenModelica and match Dymola within 1.3 % of each tracked signal's range. OpenModelica uses the flag when the model is simulated as it is (OMEdit, or `simulate()` without a `simflags` argument); a `simflags` argument replaces it, so a caller that passes its own flags must add `-noHomotopyOnFirstTry` itself. Dymola ignores the flag, and its results are unchanged. The components are unchanged, so a user model built from the same pipes may still need the flag in OpenModelica.
- `TRANSFORM.Math.linspace_2Dedge` and `TRANSFORM.Math.linspace_2Dcorner`: the loop that fills the interior is renamed from `i`/`j` to `iRow`/`jCol`. OpenModelica 1.27.1 inlines `linspace`, whose own iterator `i` then shadowed the loop's `i`. Depending on the sizes, interior values were wrong (`check_linspace_2D`: 3.125 instead of 2.5) or the simulation stopped with "Dimension 1 has bounds 1..5, got array subscript 6" (`Winding_12D` and the 2D conduction models, whose start temperatures use `linspace_2Dedge`). Dymola results are unchanged. In OpenModelica, `check_linspace_2D` now matches Dymola exactly, and `Winding_12D` and `Winding_12D_variableArea` simulate and match Dymola within 2e-4.
- Two examples used constructs the Modelica language does not allow, which Dymola accepts and OpenModelica rejects: `TRANSFORM.Fluid.Volumes.Examples.Condenser_Test` read `coolFlow.Medium.X_default` (a package constant reached through a component) and now leaves out that argument of `setState_pTX`, whose default is the medium's reference composition (the same value for water); `TRANSFORM.HeatAndMassTransfer.Examples.ExamplesFrom_NellisAndKlein.Figure_1_8_UniformThermalEnergyGeneration_Plane` took `sum(0)` of a scalar in a display-only check and now sums `wall.internalHeatModel.Q_flows ./ wall.Vs`, which is 0 here and follows the wall if heat generation is added. Values are the same; Dymola results are unchanged, and both now run in OpenModelica and match Dymola.

- `TRANSFORM.Nuclear.ReactorKinetics.Reactivity.FissionProducts_externalBalance_withTritium_withDecayHeat`: the per-species decay powers `Qs_near_i` and `Qs_far_i` are now public instead of protected. `TRANSFORM.Nuclear.ReactorKinetics.PointKinetics_L1_atomBased_external` reads `fissionProducts.Qs_near_i`, and the Modelica specification (3.6, section 4.1) does not allow reading a protected element from outside its class; Dymola tolerated it. Nothing is renamed or removed, and results are unchanged.
- `TRANSFORM.Media.Interfaces.Solids.PartialSimpleAlloy_SplineBased.specificEnthalpy` (used by `TRANSFORM.Media.Solids.Molybdenum` and `Tungsten`): in Dymola 2026x, enthalpy came out as 0, without a warning, when the temperature was a fixed value rather than one that changes during the simulation, for example `Real h = Mo.specificEnthalpy(Mo.setState_T(1000))` (237,265 J/kg is right). The function now sums the same trapezoids in a loop instead of building arrays with `cat()` and slices. Where the temperature changes during the simulation, Dymola results are unchanged (identical over 50–3600 K). The function also now runs in OpenModelica 1.27.1, whose generated C did not compile before, so the `Molybdenum` and `Tungsten` examples simulate there and match Dymola. A new test, `TRANSFORMTest.Media.Solids.AlloyEnthalpy_FixedT` (in TRANSFORM-UnitTests), records both metals at 1000 K.
- `TRANSFORM.Fluid.TraceComponents.TraceSeparator`: the trace substances entering at `port_a_carrier` are now taken with `inStream` in the equation section (a new protected variable `Cs_in_carrier`) instead of inside the algorithm. OpenModelica 1.27.1 generated C that did not compile for `inStream` in the algorithm; `TraceSeparator_Test` now runs in OpenModelica and matches Dymola. Dymola results are unchanged (`TraceSeparator_Test` identical; `MSDR_noBOP`, which uses the separator, within 2e-6).
- `TRANSFORM.Media.Interfaces.Solids.PartialSimpleAlloy.setState_T`, used by nearly every solid material: now `Inline=true`. Without it, OpenModelica 1.27.1 wrote a state record into a Real when the temperature was fixed (for example a wall's start temperature), and its generated C did not compile. `Example_2_2_1_2DFin` now runs in OpenModelica and matches Dymola; `withWallTrace` and `nParallel_withWall_StateBoundary` now build in OpenModelica but still fail later (slow simulation; start-up). Dymola results are unchanged (all 335 tests).

## [1.1.0] - 2026-11-03

### Added

- `CONTRIBUTING.md`: how to make changes without breaking user models (versions, renames, deprecations, removals) and how a release is made. A pull request template asks for tests, a changelog line and, for renames or removals, a run of the conversion guard in TRANSFORM-UnitTests.
- `CHANGELOG.md` and the `TRANSFORM.UsersGuide.ReleaseNotes` package, so that every change is recorded and each release is summarized inside the library.
- Regression tests for `TRANSFORM.Examples.MoltenSaltReactor.MSDR_noBOP` (15 signals) and the new standalone `TRANSFORM.Examples.MoltenSaltReactor.Components.Examples.DRACS_Test` (5 signals). Their baselines were recorded before the fixes for issues #111–#116.
- `TRANSFORM.Media.Interfaces.Fluids.PartialMedium` now has the function `massFraction`, which MSL 4.1.0 added to `Modelica.Media.Interfaces.PartialMedium`. `PartialPureSubstance` and `TableBased` implement it (`Xi := fill(0,0)`), so every TRANSFORM medium built on them has it. Without it, TRANSFORM fluid media were not subtypes of the Modelica.Fluid medium under MSL 4.1.0, and Dymola warned "Redeclaration requires a subtype ... missing public function massFraction" (an error in its pedantic check). This matters because Dymola 2026x ships only MSL 4.1.0. The change only adds the function; results are unchanged and user models need no change, unless your own medium extends one of these packages and already declares a `massFraction` of its own: then change that declaration to `redeclare function extends massFraction` or remove it. A new test, `TRANSFORM.Media.Examples.MassFraction_Test`, calls it on a table-based and a linear medium.

### Changed

- `TRANSFORM.Fluid.Volumes.Examples.ExpansionTank2_Test`: the outlet resistance `resistance.R` is 100 instead of 0.01. With 0.01 the tank took no water after its level settled, so no CO2 reached it and the tested tank concentration `expansionTank.C[1]` was solver noise (1e-11 to 1e-9). Now the tank is still filling when the CO2 arrives and `C[1]` rises to about 0.008. The level ends at 2.053 m instead of 2.043 m. Results of this example change.
- `TRANSFORM/package.mo` declares `version="1.1.0-dev"` and `conversion(noneFromVersion="0.5", noneFromVersion="1.0")`. The next release is 1.1.0; until then `main` carries the `-dev` version. Models written for 1.0 or 0.5, such as TRANSFORM-Training, need no change: Dymola loads them as before, and OpenModelica prints only a note that the library is compatible without conversion instead of warning that the versions differ. Versions have three parts from now on.
- `.gitignore` now tracks `TRANSFORM/Resources/Scripts/Conversion/`, the conventional home of Modelica conversion scripts. The rest of `TRANSFORM/Resources/Scripts/` stays ignored.
- `TRANSFORM.Nuclear.ReactorKinetics.Data`: new documentation explains what `C_nominal` does, that it matters only in tools that integrate the scaled trace inventories, and how to set per-species values in your own record. The 1e14 defaults are unchanged (#117). The `C_nominal` descriptions in the data records point to it. Text only.
- `README.md`: the section on checking that the library works points to TRANSFORM-UnitTests and DSTF instead of `runAll_*.mos` scripts, which no longer exist.

### Fixed

- `TRANSFORM/package.mo` declares `ExternalMedia(version="4.0.0")` in its `uses` annotation. The CoolProp media in `TRANSFORM.Media.ExternalMedia` and the supercritical CO2 examples already needed ExternalMedia, but the library did not say so (#106). ExternalMedia 4.0.0 is the release built on MSL 4.0.0; 4.1.x states that 4.0.0 models need no conversion. ExternalMedia stays optional: without it, TRANSFORM still loads in Dymola and OpenModelica (OpenModelica prints a notification with the `installPackage` command), and every model that does not use ExternalMedia works as before. Results are unchanged.
- `TRANSFORM.Utilities.Visualizers.IconColorMap_1D`: each element is colored from its own value `val[i]`; before, every element took the color of `val[1]`. The `dynColor` output changes for `n > 1`; nothing else does. No model in the library uses this block. A new test, `TRANSFORM.Utilities.Visualizers.Examples.IconColorMap_1D_Test`, checks it.
- `TRANSFORM.Media.Interfaces.Fluids.TableBased`: `MM_const` is declared as `SI.MolarMass` instead of the Modelica.Media `MolarMass` type, whose upper bound of 0.25 kg/mol was below the 0.252 kg/mol of `TableBasedTherminol66`. `PartialLinearFluid` and `PartialSimpleMedium_other` already used `SI.MolarMass`. No value changes; results are unchanged.
- `TRANSFORM.Examples.MoltenSaltReactor.Data.data_RCTR`: `rs_ring_cell` is now written as `{(i - 1)*length_reflA_ring_cell for i in 1:nARs + 1}` instead of being built from its own earlier elements, which Dymola's pedantic check rejects. The values are the same; results are unchanged.
- Array modifiers now use `each` where one value applies to every element, for example `nVs[2](each min=1)` or `Ts_start_1(each displayUnit="K")`. OpenModelica requires `each` and stopped with "possibly due to missing 'each'"; Dymola already assumed it, so results are unchanged. 188 modifiers in 77 classes changed, across `Fluid`, `HeatAndMassTransfer`, `Nuclear`, `Utilities` and `Examples`: declarations in base classes, geometry models, boundary conditions and records, and use sites in examples such as `SFR`, `CIET_nureth`, `NSSS`, `IRIS` and `GenericModule`. Nothing else in those lines changed.
- `TRANSFORM.Utilities.Visualizers.IconColorMap`, `IconColorMap_1D` and the tube colors of `TRANSFORM.HeatExchangers.GenericDistributed_HX`, `GenericDistributed_HX_Rwall` and `GenericDistributed_HX_withMass`: the color map is now held in a protected parameter `colorMapData_` before it is passed to `scalarToColor`. OpenModelica could not generate code for the old form, so every model with a fluid volume, pipe or tee failed to build there (#109). The colors are unchanged.
- `TRANSFORM.Examples.MoltenSaltReactor.MSDR_noBOP`: the drain-tank thimble convection area `surfaceAreas_thimble` passed to `DRACS` no longer multiplies by `DRACS.nP_outer_drainTank[1].nParallel`, which counted the 360 thimbles twice and made the heel-to-thimble conductance 360 times too large, on both the salt and gas sides (#112). `MSDR_noBOP` results change.
- `TRANSFORM.Examples.MoltenSaltReactor.Components.DRACS`: the water-tank make-up controller `PID_waterTank` is tuned to `k=200`, `Ti=300` instead of the `LimPID` defaults (`k=1`, `Ti=0.5`), which left the make-up flow in a barely damped oscillation of about 1 to 99 kg/s with a period of about 760 s (#113). `MSDR_noBOP` results change.
- `TRANSFORM.Examples.MoltenSaltReactor.Components.DRACS`: the NaK loop now circulates by natural convection. The downcomer `downcomer_DRACS` runs downward (`angle=-pi/2` instead of `+pi/2`, so the loop no longer climbs 36.6 m), and `resistance` has `R=1` instead of `R=-2000`, which acted as a pump (#111). The riser and downcomer each use `nV=10` volumes instead of 1, so the static-head regularization at the end of each leg no longer averages away the buoyancy head and reverses the loop (#116). `MSDR_noBOP` results change.
- `TRANSFORM.Examples.MoltenSaltReactor.Components.DRACS` and `MSDR_noBOP`: the four thimble walls start at the temperature of the fluid beside them instead of unrelated data temperatures, so there are no large heat-flow pulses at t=0 (up to 4.9 GW before) (#114). The inner walls start at the NaK start `0.5*(T_hot_dracs + T_cold_dracs)`, the outer water-tank wall at the tank start `0.5*(T_inlet_waterTank + T_outlet_waterTank)`, and in `MSDR_noBOP` the outer drain-tank wall at the heel start `data_PHX.T_inlet_tube`. All are expressions of existing parameters. Results change mainly during start-up; end values change by less than 2 %.
- `TRANSFORM.Examples.MoltenSaltReactor.Components.DRACS`: the water-tank thimble walls `thimble_outer_waterTank` and `thimble_inner_waterTank` use the water-tank thimble length `length_thimbles_waterTank` (25 ft), as their NaK pipe already did, instead of the drain-tank length (204 in). `radiation_waterTank` uses the water-tank wall areas instead of the drain-tank ones. Found while checking #111–#116. `MSDR_noBOP` results change: more heat reaches the water tanks, the NaK runs colder and the drain-tank heel ends about 6 K cooler.
- `TRANSFORM.Examples.MoltenSaltReactor.Components.DRACS`: the four NaK pipes (`thimbles_drainTank_fluid`, `riser_DRACS`, `thimbles_waterTank_fluid`, `downcomer_DRACS`) use `massDynamics=SteadyStateInitial`, so the tool computes consistent start pressures. With the default start pressures, which ignore the 18 m of hydrostatic head that the downward downcomer (#111) makes real, the loop flows at t=0 disagreed (riser −502 kg/s, downcomer +6630 kg/s) and settled within 5 ms. All loop flows now start near 130 kg/s; results after the first milliseconds change by less than 1 %.
- `TRANSFORM.Examples.MoltenSaltReactor.Components.DRACS`: the descriptions of `surfaceAreas_thimble` and `alphas_drainTank` now say element [1] is salt and [2] is gas (they said "gas and salt"). Text only.
- `TRANSFORM.Fluid.ClosureRelations.PressureLoss.Models.DistributedPipe_1D`: in `SinglePhase_Developed_2Region_NumStable`, `SinglePhase_ReynoldsRelation_NumStable`, `SinglePhase_Turbulent_MSL`, `TwoPhase_Developed_2Region_NumStable` and `TwoPhase_Developed_2Region_NumStable_alternate`, the homotopy `simplified` relation now uses `max(abs(dp_nominal), dp_small)` instead of `dp_nominal`, so pipes whose net height change is downward no longer get a negative conductance during homotopy initialization (#115). The `actual` relation and `dp_nominal` itself are unchanged.
- Graphics annotations use only standard attributes, so Dymola's pedantic check accepts them. On `Text`, the text color is `textColor` instead of `lineColor`, and the fill and line attributes that `Text` does not have (`fillColor`, `fillPattern`, `lineThickness`, `pattern`) are removed. Connection lines lose the `thickness` that had no value. 618 graphics records (537 `Text`, 81 `Line`) in 333 files, across the whole library. Annotations only: results are unchanged, and Dymola 2026x exports of every icon and diagram in those files are pixel-identical before and after.
